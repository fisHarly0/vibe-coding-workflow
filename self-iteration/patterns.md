## Pattern P-001: "存档/外部状态变更必须在第一轮 Plan 中纳入"

- **观察次数**: 3 次
- **支撑证据**: reflection-log.md 中
  - 2026-04-15 09:30（Godot 网格重构，第二轮才发现 migrator 缺失）
  - 2026-04-22 16:40（net-blog 部署，DNS 状态没记录导致跨会话重复检查）
  - 2026-04-30 20:50（误提交 .env，本质是部署涉及的状态没在 Plan 中标注）
- **现象**: 涉及"持久化状态" / "外部副作用"的任务，如果第一轮 Plan 没显式列出这些状态，后续会话往往会出现重复检查、遗漏迁移、或污染版本控制
- **推测原因**: Plan 子 Agent 默认只关心"代码改什么"，对"存档结构 / DNS / 环境变量 / git 状态"这类副作用关注度不够
- **可能改进**: 在项目 CLAUDE.md 中加入约束："Plan 子 Agent 输出方案时，必须显式列出本次任务涉及的所有外部状态（存档/DNS/env/git）。"
- **状态**: 🆕 新提取

## Pattern P-002: "git add 必须按文件名，禁止 . / -A"

- **观察次数**: 1 次
- **支撑证据**: reflection-log.md 中
  - 2026-04-30 20:50（.env 误提交事件）
- **现象**: 单次失败但代价极大（敏感信息进入 git 历史）
- **推测原因**: Agent 在追求效率时倾向于用 `git add .` 一次性 stage 所有变更
- **可能改进**: 在项目 CLAUDE.md "强约束" 章节加入：禁止使用 `git add .` / `git add -A`。无一例外。
- **状态**: 🆕 新提取
- **备注**: 虽然只观察 1 次（不满足 protocol.md STEP 2 规定的 ≥3 次），但**安全类失败属于例外** —— 1 次代价已足够大，立即升级为 pattern

## Pattern P-003: "微小 UI 改动跳过 Plan 子 Agent"

- **观察次数**: 4 次
- **支撑证据**: reflection-log.md 中
  - 2026-04-25 11:20（金币千分位）
  - （另 3 次微改动，详细条目省略）
- **现象**: 单文件、单函数级别的小改动，调用 Plan 子 Agent 反而拖慢节奏
- **推测原因**: Plan 子 Agent 设计目标是"避免短视"，对显然不需要全局规划的小改动是冗余开销
- **可能改进**: 在项目 CLAUDE.md "偏好" 章节加入：单文件 + 单函数 + ≤ 20 行改动的任务直接 Edit，不调用 Plan 子 Agent
- **状态**: 🆕 新提取

## Pattern P-004: "性能问题优先静态分析"

- **观察次数**: 2 次
- **支撑证据**: reflection-log.md 中
  - 2026-05-02 15:00（商店面板掉帧）
  - （另 1 次类似情况，详细条目省略）
- **现象**: 性能问题如果直接动手改代码，往往要试错多次；先用 Code-Review 子 Agent 静态分析能更快定位
- **推测原因**: 性能问题的根因常隐藏在"看起来无关"的代码段，需要全局视角
- **可能改进**: 项目 CLAUDE.md 加入工作流约定：性能优化类任务，第一步必调 Code-Review 子 Agent 做静态分析
- **状态**: 🆕 新提取
- **备注**: 仅 2 次观察，按 protocol.md 规定不应升级为 pattern。**留作观察，不进入 Proposal 阶段**
