# 05 - 实践案例

三个验证过本工作流的真实项目，按 **不同验证维度** 排列。

---

## 案例 1：net-blog（个人博客系统）

**当前状态**：LIVE @ hlhaya.cn

**项目类型**：从 0 到 1 的 Web 产品

**验证的核心命题**：AI 能否独立承担一个完整产品从架构到上线的全链路？

### 关键事实

- 站点已部署到生产环境，公开可访问
- 前端架构、CMS 集成、域名解析、CI/CD 全流程由 Agent 主导
- 关键架构决策（技术栈选型、数据模型、部署方案）由 Agent 提出建议，人类二选一确认

### 验证结论

- **可行性**：✅ 个人产品级 Web 应用可以由 Agent 主导落地
- **关键支撑**：HANDOFF.md 在数十次跨会话开发中保持架构一致性
- **人类介入**：仅在域名购买、生产部署等不可逆节点

## 案例 2：app note Godot 重构版

**当前状态**：持续迭代中

**项目类型**：游戏引擎大版本重构

**验证的核心命题**：在不熟悉的技术栈（Godot）上，HANDOFF.md 长链接续机制能撑起多深的工程？

### 关键事实

- 原项目（不同引擎）完整迁移到 Godot 4.x
- 单项目累计 30+ 轮跨会话接续开发
- HANDOFF.md 是接续的唯一锚点 —— 每次新会话从读 HANDOFF 开始

### 验证结论

- **可行性**：✅ HANDOFF.md 单文件可承载数十轮接续而不失真
- **关键支撑**：每次会话结束前强制更新 HANDOFF 的 "下一步行动" 与 "关键决策记录"
- **教训**：HANDOFF.md 必须保持简洁。一旦超过 ~300 行，新会话开始时会出现 "知道一切但抓不住重点" 的问题，需要主动归档历史决策

## 案例 3：TripStar 本地化深度改造

**当前状态**：本地部署完成、补丁运行稳定

**项目类型**：开源项目的深度修改

**验证的核心命题**：Agent 能否在不熟悉的开源代码库中精准定位问题、做出最小化修改？

### 关键事实

- 在不稳定网络环境下，原版 LLM 调用失败率高
- Agent 在 Explore 子 Agent 协助下定位到调用层
- 在虚拟环境（.venv）中给调用层打了重试 + 降级补丁
- 补丁不污染主代码，可随依赖升级保留

### 验证结论

- **可行性**：✅ Agent 可在陌生代码库中做外科手术式修改
- **关键支撑**：Explore 子 Agent 处理 "在哪改" 的问题，让主对话专注 "怎么改"
- **教训**：补丁位置的选择需要 Agent 在 "改源码" vs "改依赖" 之间做架构判断，这类决策必须留给人类二选一

## 横向比较

| 维度 | net-blog | Godot 重构 | TripStar 补丁 |
|------|----------|-----------|---------------|
| 技术栈熟悉度 | 中 | 低 | 中 |
| 项目体量 | 中 | 大 | 小 |
| 跨会话深度 | 中 | 极深（30+） | 浅 |
| 主要价值 | 端到端落地 | 长链接续 | 外科改造 |
| 人类介入点 | 部署 / 域名 | 架构决策 | 补丁位置选择 |

## 共同沉淀

三个项目共同验证的几条原则：

1. **HANDOFF.md 是最小公约数** —— 不管项目类型如何，跨会话接续都需要它
2. **半自主 > 全自主** —— 关键节点保留人类决策，Agent 跑得更稳
3. **Subagent 真的有用** —— Explore / Plan 拆开后，主对话上下文质量显著提升
4. **写得越克制越好** —— 不论 HANDOFF 还是 MEMORY，过度记录反而让 Agent 抓不住重点
