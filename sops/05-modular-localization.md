# 05 — 多板块项目的局部接入协议

> 项目已按板块物理隔离，想拖一个板块 / 子目录到独立会话写代码，写完贴回主仓**确定性不出问题**。

## 前置条件（缺一项不适用）

- 项目至少有 2 个明确的"板块"，物理目录分开（如 `lib/<板块A>/` + `lib/<板块B>/`）
- 板块间的代码依赖**有意识地单向**（通常是 A、B 都依赖一个 core，A 和 B 互不引用）
- 数据库 / 配置 / 构建是全仓一份（常态，本协议在它基础上工作）

## 何时不适用

- 单板块项目（全是 main）—— 直接全仓改即可
- 完全 monolithic 没有板块概念的项目 —— 先做物理重组再说
- 板块之间互相 import 互相耦合 —— 局部贴回必坏，先解耦

## TL;DR

```
拖板块目录 + core 接口签名 + 板块 HANDOFF → 独立会话改
  → tsc --noEmit → 贴回主仓 → 再 tsc / build
```

改动只动板块内部 = 安全。改了 core 对外接口 = 必须把所有调用方一起改。改 schema = 不能局部，必须全仓。

---

## 1. 接入单位

**两个并存的概念**（缺一不可）：

| 概念 | 用途 | 例子 |
|------|------|------|
| **技术板块**（物理） | 决定"文件放哪、目录结构、import 边界" | `lib/<板块>/` |
| **产品组**（认知） | 决定"一次会话做什么、任务规划、需求描述" | "我这次要改卡牌系统" |

两者**可能不重合** —— 一个技术板块可能装多个产品组。

接入会话开场必须说清两件事：

- 物理边界（拖了哪个技术板块的目录）
- 任务边界（这次只改哪个产品组的什么）

## 2. 局部修改三等级

| 等级 | 改动 | 处理方式 |
|------|------|----------|
| **安全** | 板块内部代码 / UI | 拖板块目录 → 改 → 贴回 |
| **小心** | 改 core 的对外接口签名 | 必须把所有调用方一起带上 + 同步改 |
| **不支持局部** | DB schema / 配置 / 构建链 | 必须全仓操作 + migration |

判定方法：改完之后 grep 一下你改过的 export 名，看跨板块谁引用 —— 只有自己板块内部引用 = 安全；其他板块也引用 = 小心；schema / migration 路径 = 不支持局部。

## 3. 前置清单（开会话前准备）

**必拖**：

- 板块根目录（含子目录全部）
- 该板块对应的 HANDOFF.md 或当前快照（让 Agent 5 分钟入门）
- 全局"代码地图"（让 Agent 知道板块间关系的骨架）

**Agent 可见但不必拖**（IDE 项目里看得到即可）：

- core 板块的关键 export 签名（让 Agent 知道能调什么）
- DB schema 文件（让 Agent 知道 model 名 + 字段，**但禁止改**）

**开场词模板**：

```
这是 <项目名> 的 <产品组名> 板块，物理位置 <路径>。
本次会话只改 <具体范围>，不允许：
  - 改 core 板块的任何 export 签名
  - 改 DB schema
  - 跨板块新增 import（如果本板块没引用过 X 板块，本次也不能引）
你可以：
  - 改板块内部代码 / UI / 业务逻辑
  - 调用 core 已有的 export（不改签名）
  - 新增板块内部的文件
做完跑 npx tsc --noEmit，无错才贴回主仓。
```

## 4. 跨板块稳定接口（contract）

**怎么识别** —— 给你的项目跑这两条 grep，结果就是 contract：

```bash
# 找 stock 板块依赖 core 的哪些 export
grep -rh "from '@/lib/<core板块>/" lib/<stock板块>/ | grep -oE "import .* from" | sort -u

# 找 games 板块同上
grep -rh "from '@/lib/<core板块>/" lib/<games板块>/ | grep -oE "import .* from" | sort -u
```

**契约 = 两次 grep 的交集** —— 同时被多个板块 import 的 export 是最稳定的，改它就必须全仓改。

文档化 contract 时列出**具体的函数名 + 签名**，不要笼统说"用了一些 helper"。

## 5. 收尾动作

按顺序跑：

1. `npx tsc --noEmit` —— 不需要 .env，能抓 import 错。**必过**
2. 关键 schema validator（如 `npx prisma format && npx prisma validate`） —— 即使没动 schema 也跑一遍兜底
3. 路径回贴：文件直接复制覆盖即可
4. 全仓再跑一次 `npx tsc --noEmit`
5. 如果改了 core 对外接口：必须 `npm run build` 全跑，否则不算完成
6. commit message 写 `<type>(<板块名>): <描述>`

## 6. 故障恢复

**贴回后其他板块报 import 错**：

- 你改了 core 的 export 签名但没全仓同步。grep 这个 export 全文，把所有调用方对齐
- 兜底回滚：`git diff` 看你贴回的文件，把 core 那部分 revert

**贴回后类型不匹配**：

- 板块间共享 type 定义改了。把 type 定义视为 core 的一部分，全仓同步

**Schema 报错**：

- 你不该改 schema 的。`git checkout HEAD -- <schema 文件>`

**Build 通过但生产坏了**：

- 看是否漏改了 seed / script 里 hardcode 的旧 path 或旧字段名。grep 整仓老名字

## 7. 铁律（重读 5 遍）

1. **改 core 接口必须全仓** —— core 是 contract，contract 是不能"局部"改的
2. **改 schema 必须全仓** —— 单文件 schema 无法局部
3. **跨板块新增 import 必须全仓** —— 本协议假设依赖单向，新增反向依赖前先聊架构再动手
4. **commit 一个会话一个主题** —— 别在"改卡牌"的会话顺手"改股市"
5. **贴回前必跑 tsc** —— 这是免费的安全网，跳过它早晚翻车
6. **不动 AGENT.md / spec / 协议本身** —— 用户专改，Agent 仅建议

## 8. 将来：硬约束钩子

本协议目前是文档级（靠会话遵守）。下个 phase 计划接入 lint 级模块边界约束：

- 用 `eslint-plugin-boundaries` 或 tsconfig path 限制实现
- 规则模板：板块 X 只允许 import 板块 Y 当且仅当 `X-Y` 在白名单
- 触发升级条件：发现第 1 次"局部贴回后破坏其他板块"的事故时立即升级
