# 07 — 项目档案五件套（中长线项目的接续体系）

> 单文件 HANDOFF.md 是接续体系的**轻量形态**，适合小项目。项目一旦进入"持续数周、几十次会话"的中长线阶段，单文件会膨胀、串味、新旧信息混杂。本 SOP 把它升级为**标准五件套**：一个档案目录，五类文件，各管各的事。
>
> 适用：中长线项目（预计 10+ 次会话）。不适用：临时小任务（C 场景）、周末一次性小工具（用 HANDOFF.md 就够）。

## 总览

```
<项目名>-档案/                      # 项目根目录内，进 .gitignore
├── 状态档案.md          [必备·改写式]  当前快照——下个会话的 onboarding 真源
├── vibe库资料.md        [必备·追加式]  可复用模式清单——下个项目能搬走的东西
├── 最新日志.md          [双写副本]     = 日志/ 里最新那篇的复制
├── 最新自审.md          [双写副本]     = 自我审查/ 里最新那篇的复制
├── 日志/
│   └── YYYY-MM-DD-标题.md  [累积式·按时间]  会话总结 + 决策留痕
├── 调研/
│   └── 主题.md             [累积式·按主题]  技术调研,无日期,不设"最新调研"
└── 自我审查/
    └── YYYY-MM-DD.md       [累积式·按时间]  自审报告,C/H/M/L 分级 + 跟进 checkbox
```

**起步只建必备两件**（状态档案 + vibe库），其余按需再建。不要让 AI 一开始把目录全建好。

## 每件的职责边界

### 1. 状态档案.md —— 当前快照（最重要的一件）

回答"项目现在在哪、下次该干什么"。**改写式**：每次收尾把相关段落按当下重写，不往下堆历史（历史是 `日志/` 的事）。

推荐结构（也是"接续文档"的标准六段）：

```markdown
# <项目名> 状态档案（YYYY-MM-DD 末）

## 1. 项目最新状态
<当前部署状态 / 跑在哪个 commit（hash 写 7 位）/ 可验证的事实优先：
 线上 URL、测试通过数、数据库行数，而不是"大概完成了">

## 2. 核心系统现状
| 系统 | 当前状态 | 最近改动 | 下次优先级 |
|------|---------|---------|-----------|

## 3. 下次会话该问什么 / 不该问什么
该问：<还开放的决策点>
不该问："项目怎么样 / 做到哪了" —— 这份档案就是答案

## 4. 立刻可跑的诊断命令
<2-3 条命令 + 预期输出，新会话 30 秒确认环境没坏>

## 5. 已知小尾巴
<不阻塞下一步的遗留问题，一行一条>

## 6. 用户协作风格速记
<本项目内用户的铁律，例：plan 默认 recommend / 不信全面OK报告>
```

### 2. vibe库资料.md —— 可复用模式（与状态档案严格分文件）

清单体，**追加式**，每条带最小代码片段或命令。判别标准一句话：

> **状态档案是这个项目专属的（项目变了它就过期）；vibe库是能搬去下个项目的（搬走还能用）。**

混在一起两边都废：状态档案被通用技巧稀释，vibe库被项目细节污染。

### 3. 日志/ —— 会话总结（按时间累积）

每次有实质产出的会话收尾写一篇 `YYYY-MM-DD-标题.md`：做了什么、为什么这么做、commit hash、踩了什么坑。只增不改。

### 4. 调研/ —— 技术调研（按主题累积，注意例外）

按**主题**命名（`存档方案选型.md`），不按日期。同主题新发现追加进同一份。
**例外**：调研不设根目录"最新调研"副本——因为调研按主题组织，不存在"最新"概念。

另一条重要边界：**档案里的调研 ≠ 用户决策**。新会话把调研当参考资料，不当 constraint；只有用户当面点头的才算拍板。写调研时区分"用户已拍板项"和"AI 草稿待拍板项"。

### 5. 自我审查/ —— 自审报告（每次新文件）

让 AI 对项目做的体检报告，问题按 C/H/M/L 分级，末尾放跟进 checkbox。**每次新建文件**，不往老文件追加（老报告是历史证据，要保持原样）。

## 双写副本约定（本 SOP 的关键发明）

`日志/` 和 `自我审查/` 写完新文件后，**同时把内容复制覆盖**到根目录的 `最新日志.md` / `最新自审.md`。

为什么：新会话 onboarding 只需要拖 2-3 个文件（状态档案 + 最新日志 + 当前模块 spec），不需要进子目录翻找"哪篇是最新的"。副本用**直接复制**，不用 symlink（跨平台 + 拖文件兼容性）。

## 写作守则（8 条）

1. **绝对日期**——不写"上周/前几天"，写 YYYY-MM-DD
2. **commit hash 留档**——7 位，方便 `git show` 回溯
3. **可验证事实优先**——URL / 测试数 / 行数，优于形容词
4. **vibe库 ≠ 状态档案**——严格分文件（判别标准见上）
5. **状态档案是快照不是合订本**——改写，不堆叠
6. **双写副本**——仅日志/自审；调研不双写
7. **自审每次新文件**——不追加
8. **关键决策标注拍板时间**——"2026-05-15 用户拍板选 X"，而不只是"用了 X"

## 档案为什么不进项目 git

- 档案含工作过程、协作风格、半成品判断——commit log 会被污染，公开仓会暴露细节
- 进 `.gitignore`；要版本化就回送到独立的经验仓（见 [08](08-experience-repo-and-writeback.md)）
- 代价是档案不随项目仓备份——所以中长线项目建议配经验仓

## 项目大了之后：分层档案

档案文件超过 7-8 份后，在档案目录加一个 `README.md` 作分层入口：列出"做 X 类任务拖哪几份"的对照表。此后新会话 onboarding **先拖 README**，按表选子档案，不再拖全家桶。

老的 `状态档案.md` 若已被 README 取代，把它改成一个 <2KB 的 stub（顶部明示"已升级为 README，入口在哪"）。新会话要认得出 stub，按指路走，别把 stub 当真档案用。

## 容易忘的细节

1. 升级时机：HANDOFF.md 超过 300 行或项目预期超 10 次会话 → 切五件套
2. 新会话开场**只拖必要文件**，永远不拖整个档案目录（撑爆 context）
3. 档案写入后，如果用户建了经验仓 → 触发回送（见 [08](08-experience-repo-and-writeback.md)）

## 不要做什么

- 档案进项目 git（污染 + 泄露）
- 状态档案里堆历次会话记录（那是 日志/ 的事）
- 调研写成单文件流水账（按主题拆）
- 自审往老文件追加（每次新建）
- 写完日志/自审忘了同步根目录副本（下次拖到旧的）
- 给调研也建"最新调研"副本（调研无"最新"概念）
- 用 symlink 替代复制
- 把档案里的调研当用户决策执行（参考 ≠ 拍板）
- 一开始建满五件套全目录（只建必备两件，其余按需）
