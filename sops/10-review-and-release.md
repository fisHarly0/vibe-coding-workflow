# 变更审查与发布

2026-11-06。适用于代码、配置、规范和发布变更。已有项目约束与用户授权优先。

## 提交前

明确目标、影响路径、验收方式和风险。列出可运行的项目命令，从正常入口验证用户行为，记录命令、结果和对应提交或工作树。文档变更检查链接、路径、事实与规则冲突。无法运行的检查留作未验证项。

功能和故障修复完成后，用独立上下文检查 diff、相关调用方和验收目标。可用项目已有审查工具、单独会话或已获授权的审查 agent。未授权时不自动派发 agent，也不把作者自查记成独立审查。独立审查不可用时记录缺口，按风险决定是否阻塞。

## PR 与审批

每项发现应包含文件位置、触发条件和影响。作者复现后修复，或记录误报、设计取舍及理由。与本次修改无关的旧问题单列。安全问题检查权限、输入、凭据和数据边界。未处理的真实缺陷与项目必需检查失败阻塞合并。

| 风险 | 判断依据 | 处理要求 |
|---|---|---|
| 低 | 可逆的文档或文案变更，无权限、执行或发布影响 | 完成相关验证后按已有提交授权保存 |
| 中 | 普通功能、接口或配置行为变化 | 完成行为验证和独立审查，负责人确认验收与回滚 |
| 高 | 权限、支付、数据迁移、安装更新、CI、发布和全局执行规则 | 明确影响与恢复路径，独立审查缺失时阻塞发布，按既有权限由负责人决策 |

风险由修改实际影响决定。普通文档若改变执行权限，也按高风险处理。AI 意见不能代替必需的人工审批。已有明确授权可沿用，授权未覆盖的高风险操作需确认。新提交或手工解决冲突后，重新核对受影响的证据与审批范围。

审查最多三轮。第一轮看完整修改及必要上下文，后续看新增差异和未解决项。第三轮仍未收敛时停止自动互改，记录问题并重新判断方案。同一已答复问题不重复提出，风格建议不阻塞。此轮次上限是本工作流的起始设置，后续按实践调整。

## 合并与上线

合并前核对目标分支与待发提交，运行项目要求的检查。并发 PR 使用项目支持的合并队列并验证组合结果。无队列时，在最新目标分支上集成后重新验证受影响行为。

上线前记录旧版本、目标版本、负责人、观察窗口、观测指标、异常阈值与回滚步骤。根据产品能力使用功能开关、小范围试用和分批放量。数据迁移明确备份恢复或前向修复方案，确认代码回退与数据版本兼容。发布或恢复操作沿用现有授权。

上线后检查关键用户流程和实际错误率。触发预定阈值时执行已授权的关闭开关、版本回退或恢复步骤，并验证恢复结果。复盘时把漏检案例转为项目回归检查，记录误报与审查轮数。没有线上观测时只报告本地验证结果。

## 接入与证据

项目规则中填写实际检查命令，按需采用 [审查约定模板](../templates/REVIEW.md) 和 [PR 模板](../.github/pull_request_template.md)。这些 Markdown 只表达流程。CI 阻断、保护分支、审查服务和合并队列需要项目单独配置并实际验证。

交接记录本次风险、验证范围、独立审查状态、未解决发现及回滚方式。回滚率、事故率、人工处理时间与审查轮数一起观察，持续比较同类变更。尚无基线时记录样本，不声称流程已经提升质量。
