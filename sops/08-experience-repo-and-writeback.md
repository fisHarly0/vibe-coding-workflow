# 08 — 经验沉淀仓与回送四件套

> 项目档案（[07](07-project-archive-five-piece.md)）解决"单项目怎么接续"；本 SOP 解决"多项目之间经验怎么流动、怎么不丢"。做法是建一个独立 git 仓做**跨项目经验仓**，并用**四件套闸门**保证每次回送不腐烂。
>
> 适用：并行 2+ 个项目、且打算长期用这套工作流的人。不适用：只有一个小项目（项目档案本身就够）。

## 经验仓长什么样

```
my-experience-repo/                 # 独立 git 仓（建议 private）
├── README.md            # 自描述：仓里有什么、各板块计数、最近更新日期
├── 索引.md              # 检索入口：按"想查 X 去哪"组织，只管"去哪查"
├── 变更流水.md          # 编年事件流：谁在哪天回送了什么（与索引分工：索引管空间,流水管时间）
├── 快照/
│   └── <项目名>/        # 每项目一个子目录（一定带这层,不要平铺）
│       ├── <项目名>接续档案.md   # ← 项目"状态档案"的副本（覆盖式）
│       └── <项目名>沉淀.md       # ← 项目"vibe库资料"的副本（覆盖式）
├── 踩坑笔记/            # 一坑一文件：现象 → 根因 → 解法 → 怎么预防
├── 决策日志/            # 一决策一文件：背景 → 选项 → 拍板 → 后果回看
└── 操作手册/            # 跨项目 SOP（本仓库 sops/ 的私有版,含未脱敏细节）
```

每个正式沉淀文件头部带 frontmatter（机器可读，体检脚本靠它扫描）：

```yaml
---
created: YYYY-MM-DD
project: <项目名 或 跨项目>
tags: []
status: active
triggers: [<什么场景会想查这篇>]
---
```

## 核心洞察：这类仓腐烂，缺的是执行闸门，不是规范

经验仓最常见的死法**不是**"没规范"，而是"有规范没执行"：快照写了但索引没登记（检索不到 = 白写）、README 计数停在三个月前（自描述失真）、死链累积没人扫。审视一个经验仓的健康度，先分清缺的是文档还是执行——多数时候是后者，对症下药是**装闸门**，不是写新规范。

## 回送四件套（每次缺一不可）

"回送"= 把项目档案的精华同步进经验仓。四件事是一个原子操作：

### 件一：磁盘（快照落盘）

```
项目的 状态档案.md   → 快照/<项目名>/<项目名>接续档案.md   （覆盖）
项目的 vibe库资料.md → 快照/<项目名>/<项目名>沉淀.md       （覆盖）
新踩的坑             → 踩坑笔记/<一句话现象>.md            （新建,带 frontmatter）
新拍的板             → 决策日志/<一句话决策>.md            （新建,带 frontmatter）
```

- 路径**一定带 `<项目名>/` 子目录层**；文件名前缀用项目名，不用技术栈名（同栈多项目会撞名）
- 日志/自审**不**单独落快照——精华已经沉淀在接续档案和沉淀两份里

### 件二：索引（登记检索入口）

新增的每个正式文件**同步登记进 `索引.md`**。漏登 = 检索不到 = 等于没写。
编年事件加进 `变更流水.md` 顶部（不要写进索引——索引管空间，流水管时间）。

### 件三：体检（机器扫描）

跑体检脚本（一段几十行的脚本就够），扫四样：

- **孤儿**：磁盘上有、索引里没有的文件 → 当场补登记
- **死链**：索引指向不存在的路径 → 当场修
- **计数**：各板块实际文件数 vs README 声称的数
- **frontmatter**：新文件缺 frontmatter 的 → 当场补

体检产出一份只读报告。**当场修**扫出的问题，不留到"下次"。

### 件四：自描述（刷新 README）

README 的计数跟体检报告走（勿手填），日期刷新。README 是别人（包括未来的 AI）判断这个仓是否还活着的第一眼。

### 收尾：commit + push

```bash
git status && git diff        # 先看工作区——并行会话可能留有别人的 WIP
git add <显式列出本次文件>     # 禁止 git add .
git commit -m "回送 <项目名> <事件一句话> — YYYY-MM-DD"
git push
```

## 触发模型：隐式直接做，含糊才问

| 触发 | AI 的动作 |
|------|----------|
| **隐式**：本次会话项目档案有任何写入 | 收尾时**直接执行四件套 + 告知用户**，不问"要不要回送" |
| **显式清晰**："沉淀一下 / 记一下 / 收尾" | 直接执行 |
| **显式含糊**：触发语指向不明 | 先问清范围再执行 |

为什么隐式也直接做：实践发现"每次都问"的结局是用户嫌烦 → AI 学会不问 → 静默跳过 → 漏沉淀。直接做 + 告知（用户可叫停）比请示制可靠。**但绝不静默跳过**——跳过本身要说出来。

## 信息流全景

```
            写入                  回送(四件套)
单次会话 ────────→ 项目档案 ──────────────────→ 经验仓
                  (项目根,不入git)              (独立git仓,版本化)
                      ↑                            │
                      └────── onboard 新会话 ←─────┘
                              (接续档案/沉淀 可直接喂给新机器上的新 AI)
```

经验仓里每个项目的"接续档案 + 沉淀"两份快照，等价于该项目的**便携 onboarding 包**——换电脑、换 Agent 工具，拖这两份就能接上。

## 容易忘的细节

1. 快照是**覆盖**不是追加（它是项目状态档案的镜像，镜像就该跟源一致）
2. 踩坑笔记的文件名写**现象**不写结论（检索时你记得的是现象）
3. 决策日志要有"后果回看"段——半年后补一行"这个决策后来被证明对/错"
4. 体检频率：每次回送顺手跑；至少每月一次全仓体检

## 不要做什么

- 只落磁盘不登索引（四件套缺一就是半套，下次找不到）
- `git add .`（带上并行会话的 WIP 和敏感文件）
- 快照平铺不建 `<项目名>/` 子目录（项目一多就乱）
- 新文件漏 frontmatter（体检脚本扫不到它）
- 回送时跳过体检（漂移会复利累积）
- README 计数手填（必然失真，跟体检走）
- 把"规范写进了文档"当成"问题解决了"（没有执行闸门的规范对下一次行为零约束）
- 静默跳过回送（跳过可以，但要说出来让用户知道）
