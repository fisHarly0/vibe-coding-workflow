# 04 — 双 Agent 协作模式（A 规划+检验 / B 执行）

> 单 Agent 装不下的中大型项目，需要持续多 turn 工作。一边规划+检验，一边执行+自检，用 `COLLAB_LOG.md` 异步通信，Monitor + 心跳互相唤醒。
>
> **B 不限于另一个 Claude——Codex / GPT 或其他执行体同样适用，A 是大脑，B 是手脚**。

## 一、什么时候值得用 / 不要用

**值得**：

- 一个 turn 写不完的功能（>200 行改动 + 跨 6+ 文件）
- 需要持续多日 / 多 turn 工作的项目
- 经常有用户突然抽查、要求快速回应
- 项目本身有较强的"规划 vs 执行"分层（规格 → 实现 → 检验）

**不要**：

- 一个 turn 能搞定的小修改（直接单 Agent 更快）
- 探索性任务（不知道要做什么），A 没东西可派
- 用户全程在看，不需要异步（协作 overhead 反而拖慢）

## 二、角色定位

| 角色 | 责任 | 不做的事 |
|------|------|----------|
| **A** | 出规格（`#NNN` 任务）/ 检验 / 跟用户对话 / 切档 / git push | 不写实现代码 |
| **B** | 实现规格 / 自检 / 写完成报告 / 等待期做调研 | 不出规格 / 不 push / 不直接跟用户说话 |
| **用户** | 起会话 / 最终裁判 / 决定路径 / 抽查 | — |

A 和 B **不直接通信**，只通过 `collab/COLLAB_LOG.md` 异步交换。

## 三、必备文件结构

```
project-root/
├── HANDOFF.md                  # 项目状态（共享 source of truth）
├── collab/
│   ├── COLLAB_LOG.md           # 主协作日志（A↔B 通信）
│   └── B_ONBOARDING.md         # 给新 B 会话粘贴的入场指令
└── collab-logs/                # 切档后的归档（切档前可不存在）
    └── INDEX.md                # 历史日志索引，标记当前活跃 log
```

`COLLAB_LOG.md` 用 `### YYYY-MM-DD [角色] 类型 — 标题` 作为条目分隔符，Monitor 通过这条正则的计数变化感知新条目。

## 四、A 出 spec 的「5 字段规范」⭐

A 派给 B 的每条子任务必须包含 5 个字段，**缺一不可**。没有的字段写"无"占位，禁止省略。

| # | 字段 | 内容 | 没有时怎么写 |
|---|------|------|--------------|
| 1 | **目标 file@line** | 改哪个文件第几行 | 新建文件就写"新建 `path/foo.gd`" |
| 2 | **API + 签名引用** | 调哪个 API + 签名出处 | "无 API 调用，纯字面量改动" |
| 3 | **前置验证命令** | 写之前必须跑的命令（grep / cat / find / etc） | "无前置验证（首次新建无需 grep）" |
| 4 | **后置验证命令** | 写之后必须跑的命令（编译 / lint / test） | "无可执行验证，交用户 F5 实测" |
| 5 | **验收标准 N 条** | B 自检 + A 检验时对照的 ✅/🟡/❌ 清单 | 至少写 1 条，禁止"凭感觉" |

**为什么这 5 个字段**：早期实战暴露的协作翻车里，多数根因是"A 指令笼统"（API 签名错 / 字符串转义错 / 软约束失效）。笼统指令 → B 一字不差落地 → 运行时才暴露。**这 5 个字段把验证从"事后审计"前移到"出 spec 那一刻"，并给 B 完成报告的 ✅/🟡/❌ 提供真正的对照物**。

### 反例 vs 正例

```
反例
#002.R1 — Hero 死亡 toast
在 hero 死亡时调 FX 显示死亡提示，文案要悲壮一点。
```

指了 FX 但没说签名、参数、文案格式。B 落地必出错。

```
正例
#002.R1 — Hero 死亡 toast

1. 目标 file@line: Game.gd:1512 (_resolve_hero_death 函数内)
2. API + 签名: FX.show_toast(title, desc, life)，签名见 FX.gd:81
3. 前置验证: grep -n 'FX.show_toast' scripts/   (确认现有 3 参数风格)
4. 后置验证: 在 Editor 里手动调 _resolve_hero_death，看 toast 弹出
5. 验收标准:
   - title = "💀 阵亡"
   - desc = hero name（避免拼接进 title）
   - life = 4.5（比默认 3.5 更长，让玩家看清）
   - 调用方 Game.gd:1512 落地后能 godot --check-only 通过
```

## 五、命名空间（`[A]` / `[B]` 标记）

写日志条目永远以 `### YYYY-MM-DD [A]` 或 `### YYYY-MM-DD [B]` 开头。**A 监听 `[B]` 计数变化，B 监听 `[A]` 计数变化** —— 这样自己写不会自激。

| 标记 | 类型 | 谁写 | 何时写 |
|------|------|------|--------|
| `[A] #NNN — 标题` | 派任务 | A | 出新规格 |
| `[A] 检验 #NNN — 通过/打回` | 检验结论 | A | B 报告完成后 |
| `[A] 备注 — 用户抽查中途巡查` | 抽查盘点 | A | 用户突然问"做到哪了" |
| `[B] 入场就绪` | 接手 | B | 读完入场文档 + 扫代码后 |
| `[B] 监听就绪` | Monitor 部署完成 | B | 起完 Monitor + 心跳 |
| `[B] 完成 #NNN — 标题` | 完成报告 | B | 干完一个任务 |
| `[B] 调研 — 主题` | 等待期调研 | B | A 工作期间不空转 |

## 六、工作循环

```
T0  用户启 B 会话（粘 B_ONBOARDING）
T1  B 读入场文档 + 扫代码      → [B] 入场就绪
T2  B 部署 Monitor + 心跳      → [B] 监听就绪
T3  A 出规格                   → [A] #001
T4  B 拆子任务，多 turn 干     （每 turn 末 ScheduleWakeup 续命）
T5  B 写完成报告               → [B] 完成 #001
T6  A 看代码 + 对照验收标准    → [A] 检验 #001 通过/打回
T7  通过 → 等下一任务期间，B 写 [B] 调研 — 主题
...
Tn  日志 ≥1000 行 → A 切档 → B 跟随到新 log
```

每 turn **7-10 个工具调用上限**；超过用 `ScheduleWakeup` 续下一 turn。

## 七、Monitor + 心跳

**Monitor 主导**（~20s 延迟，事件即时触发）+ **心跳兜底**（防 watcher 异常 / 系统休眠）。

**心跳间隔避开"worst-of-both"区**：prompt cache TTL = 5 分钟（300s）。睡过这个就掉缓存。

| 间隔 | 评级 | 用法 |
|------|------|------|
| 60–270s | 缓存热 | 主动监控期、刚下完任务想短时间检查 |
| 300–1200s | **避开** | 付了缓存失效但只多等几分钟，worst-of-both |
| 1200–1800s | 划算 | 默认空转兜底 |
| 1800–3600s | 长等待 | 没任务 / 等用户 |

**默认值**：**1800 秒（30 分钟）** 当无具体信号要看。

## 八、Monitor bash 模板

```bash
file="path/to/collab/COLLAB_LOG.md"
last_a=$(grep -cE '^### .* \[A\]' "$file" 2>/dev/null)
last_a=${last_a:-0}
echo "WATCH_READY baseline_A_entries=$last_a"
while true; do
  current=$(grep -cE '^### .* \[A\]' "$file" 2>/dev/null)
  current=${current:-0}
  if [ "$current" -gt "$last_a" ]; then
    echo "NEW_A_ENTRY total=$current prev=$last_a time=$(date +%H:%M:%S)"
    last_a=$current
  fi
  sleep 20  # 20s 轮询；30s+ 触感发滞后，10s- 浪费 CPU
done
```

- `persistent: true` 跑到 `TaskStop` 或会话结束
- B 端把 `\[A\]` 改成 `\[B\]`；A 端反之
- **不要用 mtime 监听**，会自激震荡；用计数监听

## 九、B 完成报告模板

```markdown
### YYYY-MM-DD [B] 完成 #NNN — 标题

**总览**
- 新增文件 N：path1 / path2
- 修改文件 M：path3 / ...
- 总改动 ~+L 行（落预估区间）
- 静态检查：通过 / 待 A 验证

**改动清单（按文件 + file@line）**
| 文件 | 行号区间 | 改了什么 |

**自检对照 A 的 N 条验收标准**
| # | 验收点 | 状态 ✅/🟡/❌ | 备注 |

**与 A 规格的偏差（≤5 处）**
1. **A 规格 X，B 实际 Y**：理由 + 影响 + 是否可改回

**已知风险 / 边角**

**待 A / 用户实测项**（无运行时环境时 Agent 无法验的部分）
```

判据：

- ✅ = 代码层符合且能复核
- 🟡 = 代码层符合但需运行时验证（F5 / 浏览器测试）
- ❌ = 没做 / 跟规格冲突

## 十、容易忘的细节

1. **mtime watcher 会自激震荡** —— 一定用 `### .* \[X\]` **计数 watcher**
2. **路径错切立即重建，不要心疼前面工作** —— 用户切目录时，A 立即停旧 Monitor + 完整重建协作文件到新路径
3. **用户抽查 ≠ 正式检验** —— 用户突然问"做到哪了"，A 直接 grep 代码盘点，**不依赖 B 日志报告**
4. **A 出规格前必须 grep 现有命名空间** —— 字段名 / 函数名 / 信号名按项目实际，不按设计稿强加
5. **B 完成报告必须 `file@line`** —— 没行号的报告 = 没法复核 = 等于没干
6. **检验时留 5-7 项给用户跑** —— 运行时错误（F5 / 浏览器 / 真机）Agent 无法验，必须列清单交给用户

## 十一、Git 工作流约定

**仅 A 端 push**，避免双端 race。

A 在写 `[A] 检验 #NNN 通过` 的同 turn 内执行：

```bash
git add .
git status        # 扫一眼，防止 secret / 调试导出物误纳入
git commit -m "<中文>：做了什么 + 为什么"   # 1 行 ≤50 字
git push
```

报错状态绝不 push；push 失败重试 1 次后报告用户。

## 十二、不要做什么

- mtime 监听 —— 用计数监听
- 双端都 push —— 仅 A 端 git，B 只写代码
- 300–1200 秒心跳间隔 —— worst-of-both 区
- 30 分钟轮询代替 Monitor —— 太慢且浪费 token
- B 藏偏差 —— "全部 ✅ 无偏差"通常说明心里有数但不敢写；主动列 ≤5 处偏差是好工作的标志
- B 直接跟用户说话 —— B 只对 A 负责，所有对外通信走 A
- 在 B 还没 `[B] 监听就绪` 前下任务 —— Monitor 没起来，任务会被错过
